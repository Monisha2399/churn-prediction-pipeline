# Data Documentation

## Overview

This project uses a hybrid dataset: real CRM data from Kaggle combined with
synthetically generated behavioural logs and support tickets.

---

## 1. CRM Data (from Kaggle)

**Source:** IBM Telco Customer Churn dataset  
**URL:** https://www.kaggle.com/datasets/blastchar/telco-customer-churn  
**Size:** ~7,043 customers  
**License:** Community Data License Agreement

The original dataset contains customer demographics, subscription details,
monthly charges, and a historical churn label. We enrich it with:

- `signup_date` — derived from `tenure` (months before snapshot)
- `churn_date` — assigned synthetically (see Label Definition below)

---

## 2. Behavioural Logs (synthetic)

Generated by `scripts/generate_data.py` with `RANDOM_SEED=42`.

| Column | Type | Description |
|--------|------|-------------|
| customer_id | string | Foreign key to customers |
| event_date | date | Date of activity |
| logins | integer | Number of logins that day |
| session_minutes | float | Total session time (minutes) |
| features_used | integer | Distinct product features used |
| failed_payments | integer | Failed payment attempts |
| support_calls | integer | Support calls made |

**Signal design:**  
Churners show a declining usage pattern in the 60 days before churn, with
added Gaussian noise. ~30% of loyal customers also show dips (noise). This
produces realistic difficulty — ROC-AUC of 0.99 would indicate leakage.

---

## 3. Support Tickets (synthetic)

Generated by `scripts/generate_data.py` with `RANDOM_SEED=42`.

| Column | Type | Description |
|--------|------|-------------|
| ticket_id | serial | Primary key |
| customer_id | string | Foreign key |
| created_at | timestamp | Ticket creation time |
| resolved_at | timestamp | Resolution time (nullable) |
| category | enum | billing / technical / cancellation / general |
| priority | enum | low / medium / high / critical |
| status | enum | open / resolved / escalated |
| subject | text | Short summary |
| body | text | Full ticket text |

**Signal design:**  
Churners skew toward complaint templates (65% probability vs 25% for non-churners),
higher-priority tickets, and escalations. However, some non-churners also
submit complaints, and some churners submit neutral enquiries — intentionally
noisy to prevent unrealistically clean NLP separation.

## 4. Label Definition

> **This is the most important design decision. Read carefully.**

For each customer at snapshot date **T**:

```
label = 1  if  churn_date ∈ (T, T + 30 days]
label = 0  otherwise
```

**Rules enforced:**
- Features use ONLY data with `timestamp < T`
- `churn_date` itself is never a feature — only the label
- Train/test split is **time-based** (earlier snapshots → train, latest → test)
- Random splits are NEVER used — they cause data leakage in temporal data

**Churn rate:** ~15–20% positive class (imbalanced — use `class_weight="balanced"`)

---

## 5. Reproducibility

All synthetic generation is seeded:

```bash
RANDOM_SEED=42 python scripts/generate_data.py
```

The `RANDOM_SEED` is logged as an MLflow parameter on every training run.
